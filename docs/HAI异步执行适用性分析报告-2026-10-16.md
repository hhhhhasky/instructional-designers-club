# HAI Chat 与 Work 异步执行适用性分析

分析日期：2026-10-16（北京时间）。本报告提供机制分析与技术建议，不代表开发排期或发布授权；项目状态统一见《项目需求与开发进展》。

## 1. 结论

**需要继续异步化，优先处理 PPT 生成及 PPT 逐页生图，其次处理 Work 文本产物；普通 Chat 保留即时流式交互。独立图片生成已经完成核心异步改造，但还没有无人值守收图能力。**

判断依据不是“请求里用了 async”，而是：用户离开页面后，任务能否独立推进；执行实例被终止后，能否找回原任务或从已完成阶段继续；重试能否避免重复生成、重复产物和重复结算。

推荐方向：**Chat 流式回答，Work 后台执行，页面通过查询或订阅展示进展；图片由供应商异步生成，本站分次查单并保存结果。** 流式展示与后台任务可以并存。

| 功能 | 当前执行方式 | 判断 | 技术优先级 |
|---|---|---|---|
| 普通聊天、追问 | SSE 实时推送正文，最终写入消息 | 保留流式，补断线与持久化保护 | 可靠性 P1；完整后台化 P2 |
| Chat 自动评估与重写 | 本地规则评估，必要时在同一 SSE 请求内再次调用模型 | 评估保留当前方式；重写先补草稿持久化，长重写再考虑任务化 | P2 |
| 教案生成：公开课设计、教学设计 | 同一 Edge 请求内收集完整模型输出，再存产物；SSE 主要发进度 | 应改为持久化后台任务 | P1 |
| 教案诊断 → 优化教案 | 两次用户触发的操作，各自走相同 Work 执行链路 | 两次各自任务化，保留用户确认步骤 | P1 |
| 环节优化、教案诊断报告 | 与长教案共用 Work 执行器 | 建议接入同一后台任务机制；短输出工具可随后迁移 | P2，复用 P1 基础能力 |
| Work 追改、重生成、失败重试 | 重新发起 Work SSE 请求 | 随对应工具一起异步化 | 同对应工具 |
| 独立图片生成，含参考图修改 | 提交供应商任务后返回，浏览器约每 10 秒查询；按需保存 R2 | 核心已异步，优先验收恢复链路；离线自动收图是后续增强 | P1 验收/增强 |
| PPT 文本、可编辑结构生成 | 多次模型调用串联在同一 HTTP 请求中，结束才返回 JSON | 必须优先异步化，并按阶段恢复 | P0 |
| 纯图片 PPT：大纲、视觉、生图参数 | 人工确认切开了部分步骤；每一步内部仍同步等待模型完成 | 每个自动阶段异步化，人工确认继续保留 | P0/P1，随 PPT 主链路 |
| PPT 配图、纯图片 PPT 每页图片 | 浏览器逐页调用；每次 Edge 请求内长轮询供应商 | 必须优先异步化，并把整套任务推进移到服务端 | P0 |
| 互动网页课件生成 | 素材、大纲、HTML 连续调用；HTML 不合格可能再调一次 | 与 PPT 共用的长任务链路一起改 | P1 |
| PPTX、Word、Markdown、HTML 导出 | 主要在浏览器基于已有结果生成文件 | 目前保留；大型 PPTX 先测内存与耗时，再决定服务端导出 | P2，条件触发 |
| 素材上传解析 | 上传后同步调用解析，Work 表单等待解析结束 | 当前小文本/Word 可保留；大文件/OCR/批量解析时再任务化 | P2，条件触发 |
| 个性化开场问题、普通保存/读取 | 短请求 | 暂无充分理由改成任务队列 | 保留 |

P0/P1/P2 是本报告提出的技术建议顺序，尚未确认进入开发。P0 表示当前架构暴露最明显的长任务风险，不表示已证明所有用户请求都会失败。

## 3. 为什么“流式”和“有任务表”仍不够

当前存在三类不同机制：

1. **请求内流式生成**：Chat、Work。连接能显示进度，但执行本身仍发生在该次函数调用中。
2. **请求内长等待**：PPT 模型链路与逐页生图。上游可能是流式或异步接口，下游 HTTP 仍等待最终结果。
3. **提交与取结果分离**：新版独立生图。供应商持续执行，本站不必保持一个函数实例等待数分钟。

Work 的 `queued/running` 行和每 3 秒详情查询已经解决部分展示与回访问题，但没有发现独立于原请求的持久执行器、领取任务和中断后重启机制。因此它具备“任务记录”，尚不具备完整的“后台任务执行”。已有 `safeSendSse` 会保护断开后的事件发送，不能笼统认定关闭网页就必然终止；同样也不能据此承诺关闭网页或平台终止实例后一定能完成。

Supabase 当前官方文档区分实例墙钟上限与请求空闲超时：Free 为 150 秒墙钟，付费方案为 400 秒，请求空闲超时为 150 秒。本项目历史排查确有约 150 秒 `WallClockTime` 记录，但本次没有核实当前订阅及实际运行上限，不能把 150 秒称为所有线上调用的固定上限。[官方运行限制](https://supabase.com/docs/guides/functions/limits)

`EdgeRuntime.waitUntil` 可在返回响应后继续处理，但仍受实例墙钟、CPU 与内存上限限制。因此仅把现有长链路包进 `waitUntil` 并返回 202，不能提供持久执行和故障恢复。[官方后台任务说明](https://supabase.com/docs/guides/functions/background-tasks)

## 4. PPT 是最应先改的部分

### 4.1 文本与结构生成：多个长步骤占用同一个请求

可编辑 PPT 依次执行素材补全、逐页大纲、组件布局设计；互动课件最后生成 HTML，必要时重试。每次模型调用配置 180 秒预算，但前三次仍在同一个请求内。

三个阶段的配置预算合计可达 540 秒，互动 HTML 再重试时可达 720 秒；这是配置预算相加，不是实测耗时，也不是平台会允许它执行这么久。即使每阶段都没有超时，整条链路仍可能先遇到请求或实例限制。

已有素材和大纲中间结果写库，这是可复用的基础；但目前没有从最后成功阶段自动继续的执行入口。典型失败场景是：素材和大纲已经成功并结算，第三阶段连接失败；用户重新生成会创建新版本，再执行上游阶段，产生额外等待和费用。

**建议**：创建记录后尽早返回任务编号；每个自动阶段独立执行、保存状态和结果，再调度下一阶段。重新进入页面能读到当前阶段；第三阶段失败仅重做第三阶段。单次模型调用本身过长时，仍需调整任务粒度或执行环境，不能仅靠拆 HTTP 解决。

纯图片 PPT 已有“大纲待确认”“视觉待确认”两个持久状态，应保留。异步执行器在这些状态暂停，用户确认后再推进；不自动跳过确认。需注意其 `completed` 当前表示结构/生图参数完成，并不等于整套图片已就绪，页面应同时表达配图完成度。

### 4.2 逐页生图：供应商异步，本站仍在单请求中等待

当前共享适配器先创建供应商任务，再每 3 秒查询，默认最多等 140 秒；创建请求另有 30 秒上限，后续还要查询及写 R2。因此“140 秒轮询”也不是整个请求的 140 秒总预算。

页面通过 `for ... await` 逐张处理图片。后端虽然保留并发池代码，但当前单次请求只处理一个页面，并发池不意味着整套 PPT 已在后台执行。页面关闭后，没有独立任务执行器负责可靠推进未提交的后续页面；已有页面也不能保证在实例终止后继续收图。

更严重的是供应商编号保存时机：编号先存在适配器局部变量里，通常到成功或特定任务错误后才合并进 `deck_spec`，最终再写数据库。平台在这之前硬终止、查单网络异常或结果存储失败，都有丢失恢复依据的风险。

本次故障模拟使用假 fetch，创建返回 `accepted-task`，第一次查询抛 `TypeError`，实际输出为 `retainedTaskId=null`。这确认了网络异常路径不会像已有的显式轮询超时路径那样保留任务编号；没有请求真实供应商。既有超时续查测试虽然通过，覆盖不到这个失败路径。

此外，当前配图路径先保存 R2、再结算、最后写课件 JSON；结算后写课件失败存在交付状态不一致风险。不能声称已经造成重复扣费，但必须在异步改造中保证保存产物引用与结算可恢复，并逐张保持幂等。

**建议**：按课件、页面及生成版本保存独立图片执行记录；供应商受理后立即持久化编号，每次只查一次状态。未完成保留等待状态，临时网络错误重试查原单。服务端根据持久化页面任务推进整套课件，前端只负责展示和用户控制。各页分别成功、失败及重试，最后汇总整套完成度；避免并发任务覆盖整份 `deck_spec`。

## 5. Work 教案与环节优化应共用后台执行机制

公开课设计、教学设计、教案诊断、环节优化及追改都走 `hai-work`。后端从上游流里收集完整正文，完成后一次落库，前端主要接收 ready、进度、心跳和 done；这类操作本来就是“交付一个成品”，适合后台任务。

项目既有 2026-08-31 排查记录显示：一次 Pro 任务约 149.5 秒被墙钟终止；当时近 30 天成功记录中，Pro 不开 thinking 的平均/P95 为 112.7/136.9 秒，Flash 为 77.6/131.7 秒。这是历史样本，不代表当前耗时，但足以说明长教案确实到过执行边界。

**优先迁移长教案、诊断后的优化教案及长文追改；短诊断和环节优化随后复用同一执行器。** 没必要给四个工具各建一套队列，也没有证据要求先把所有短操作全部后台化。

改造必须一并处理三件事：

- **3 分钟回收冲突**：当前详情读取会触发过期校正。未来合法运行超过 3 分钟时，旧规则会把它判失败并结束用量预留。应根据实际领取租约、执行心跳和执行截止时间识别失联，区分排队与执行，保留失联回收能力。
- **请求复用**：当前已经有 clientRequestId 幂等和成功产物回放；但同编号处于运行中时返回“正在处理或上次未完成”的错误事件。未来应返回现有任务及状态，页面断线后复用原编号，不以新请求替代查单。
- **单次模型上限**：当前模型调用硬上限为 140 秒。加一个队列不会自动让这次调用超过 140 秒，更不会把普通流式模型变成可通过 taskId 查询的供应商任务。必须明确单次调用预算和承载环境；单次调用被终止时，通常只能重做该模型步骤，不能承诺从丢失的某个 token 接着生成。

已有 Work 任务、run、产物版本、输入及 Skill 快照、用量记录和详情轮询均可复用。异步后后台执行不应依赖用户浏览器持续持有登录会话；执行器用受控服务身份处理已授权任务，并在服务端约束所有权和额度。

## 6. 普通 Chat 保留流式，先补可靠性

普通对话需要边生成边阅读，整体改成“排队，完成后一次取答案”会削弱体验，目前没有足够证据支持这样改。

但 Chat 当前也有可靠性缺口：正文先通过 SSE 展示，最终回答在生成及可选重写完成后才写 `hai_messages`；直接 `sendSse` 没有 Work 同等的断连保护。若事件发送失败进入异常路径，用户已读到的草稿可能没有保存。前端每次发送生成新 clientRequestId，也没有实现同一轮消息生成的可恢复查单。

建议先把每轮请求、助手草稿和完成状态建立关联；按阶段或适当间隔保存草稿，断线后可以读取已保存内容，明确区分草稿、失败和完成；避免每个 token 写一次数据库。保护事件发送失败与业务结果落库的边界，并处理重复发送同一轮请求。

自动评估器目前是本地规则计算，不是另一个远程模型调用，不值得单独排队。必要重写会第二次调用模型，且开始前清空前端草稿；应先保存原草稿及重写状态。将来确有长篇研究或多工具对话需求，再引入“后台执行 + 可恢复流式观察”。当前普通聊天无需先承担这套完整复杂度。

## 7. 独立生图：已有异步，边界是离线自动收图

线上 v18 已实现供应商提交与完成分离；业务编号先保存，生成期间不由本站长轮询，status 每次查一次并按需存 R2；前端每次查询完成后再等待约 10 秒。参考图上传和供应商受理仍会在提交请求内等待，这与整个生成过程已经异步并不矛盾。

应保留已有所有权检查、事务锁、请求幂等及图片加载确认后单次结算，不需要再建一套独立生图系统。重点完成真实长任务、刷新、关闭后回访、回执丢失、R2 短暂故障和确认断网的验收。

当前浏览器关闭后，第三方可以继续生成，但本站不会主动查询并保存图片；必须有人回访触发收图。内部既有集成文档记载第三方结果 URL 有 24 小时有效期，本轮外部文档未成功访问，**24 小时口径待再次核实**。可以确认的架构问题是：结果若只在供应商临时 URL 保留，长期不回访可能失去下载机会。

若产品需要“关闭网页后自动完成并永久保存”，应补服务端定时查单，或在供应商支持且协议核实后接 webhook。后台收图与用户确认扣费分开，自动保存不应擅自改为自动扣费。与 PPT 生图共享提交/查单/保存能力时，也须保留两类产品已有的计费差异。

## 8. 建议采用的最小执行结构

沿用 Supabase 中的任务与产物记录，补足现有执行状态和阶段信息；不必预先引入一个覆盖所有操作的大型工作流平台。

```text
用户提交 → 校验并保存请求/输入 → 返回任务编号
                                   ↓
                         可重新领取的执行器
                                   ↓
                 领取一个阶段 → 执行 → 保存结果和状态
                                   ↓
                  下一阶段 / 等待用户确认 / 完成

页面打开时：查询或订阅状态，可选观察增量正文
页面关闭时：执行与收图仍由服务端推进
```

每个任务需要稳定请求编号、阶段输出、有限重试、领取租约/心跳、产物关联和结算依据。使用主键、唯一约束、事务及常规测试解决重复领取、重复保存、重复结算；本报告不建议增加额外 hash、冻结 contract 或发布门禁。

执行器不能只是“记录 queued 然后无人领取”。选择执行承载时必须按任务粒度核实运行时限；短阶段可以继续用受调度的 Edge 调用，无法在其上限内完成的单模型任务需要更合适的执行环境或改变生成粒度。本轮只提出约束，不凭推测指定供应商队列产品或模型异步接口。

图片应使用“提交一次，反复查原单”；文本模型若没有供应商任务查询及幂等支持，网络在受理时中断会存在是否已执行的不确定性。本站可以保证产物和结算幂等，但不能凭本地任务表承诺供应商永远只计算一次。须记录尝试，避免对受理不明的请求盲目重发。

建议验收重点：关闭页面后后续阶段/后续图片继续推进；刷新后找回同一任务；实例中断后从最后成功阶段恢复；模拟供应商受理后回执丢失及查单网络错误；重复提交、两个页面同时打开时不产生重复产物/结算；用户确认暂停被保留；失败阶段重试不重跑已成功阶段；超过 3 分钟的合法 Work 任务不被旧规则误关；已保存产物与结算失败可以对账恢复。取消观察与取消执行需要区分，供应商已受理的任务能否取消及费用如何处理应如实表达。
